# AWWWARDS MAXIMUM — MASTER PORTFOLIO DIRECTIVE

## 0. PRIMARY MISSION

Your mission is to evolve the EXISTING portfolio into the strongest possible version of itself and maximize its chances of reaching genuine world-class portfolio quality comparable to:

* Awwwards Site of the Day
* Awwwards Developer Award
* top creative developer portfolios
* top independent designer portfolios
* leading digital studios
* exceptional interactive editorial websites

This is not a routine frontend cleanup task.

This is:

**CREATIVE DIRECTION + INTERACTION DESIGN + VISUAL DESIGN + MOTION DESIGN + UX + FRONTEND ENGINEERING + PERFORMANCE + POLISH.**

The target is not merely:

* clean
* modern
* professional
* responsive
* technically correct

The target is:

**distinctive, memorable, premium, surprising, coherent, technically excellent, emotionally engaging, and clearly custom-built.**

There is no way to guarantee an Awwwards win.

However, every meaningful decision should maximize the probability of reaching that quality level.

---

# 1. THE MOST IMPORTANT RULE

Optimize for:

# MAXIMUM PERCEIVED QUALITY IMPROVEMENT PER TOKEN

Do NOT optimize for:

* number of changes
* number of files modified
* number of fixes
* number of commits
* number of audit findings
* amount of code written
* amount of technical reporting
* amount of testing performed
* amount of time spent

The visitor does not care how many things changed.

The visitor cares about how exceptional the final experience feels.

---

# 2. NO COMPLETE DESTRUCTIVE REDESIGN

Do NOT perform a complete redesign from scratch by default.

Do NOT:

* delete the entire existing design
* rebuild every page from zero
* rewrite all components
* rewrite all CSS
* replace the whole design system
* replace the framework
* rewrite routing
* rebuild working architecture
* recreate already-good interactions
* remove strong existing ideas simply because a new idea exists

A full rebuild is extremely expensive in tokens and implementation effort.

The existing portfolio contains accumulated value.

Preserve that value.

---

# 3. IMPORTANT: NO FULL REDESIGN DOES NOT MEAN SMALL CHANGES ONLY

This rule is critical.

You are NOT restricted to tiny improvements.

You are strongly encouraged to:

* add new experiences
* add new sections
* add new interactions
* add new transitions
* add new creative features
* significantly transform weak sections
* improve art direction
* introduce sophisticated motion
* replace generic components
* upgrade visual systems
* create signature moments

The restriction applies only to unnecessary destruction of the entire existing foundation.

Think:

**EVOLUTION + EXPANSION + TARGETED TRANSFORMATION**

not:

**DELETE EVERYTHING + START AGAIN**

---

# 4. PRESERVE → IMPROVE → ADD → REPLACE ONLY WHEN NECESSARY

Use this order.

## 1. PRESERVE

Keep everything already strong.

## 2. IMPROVE

Upgrade things that are good but underdeveloped.

## 3. ADD

Create missing high-impact experiences.

## 4. REPLACE

Replace specific weak or generic areas when upgrading them is not enough.

## 5. FULL REBUILD

Only as an absolute last resort when a specific isolated system is fundamentally broken.

Never default to Step 5.

---

# 5. TARGETED TRANSFORMATIONS ARE ENCOURAGED

A major transformation of ONE important area is completely allowed.

Examples:

* completely upgrade the hero
* replace generic project cards
* create a better navigation experience
* introduce a new page-transition system
* transform a weak About section
* transform project navigation
* improve case-study storytelling
* rebuild a generic footer/contact experience
* introduce a new project index
* create a completely new motion system

This is NOT considered a forbidden full redesign.

This is:

**HIGH-IMPACT TARGETED TRANSFORMATION.**

---

# 6. START EVERY MEANINGFUL SESSION BY ZOOMING OUT

Before touching code, inspect the current website as a complete experience.

Understand:

* what already works
* what looks premium
* what looks generic
* what feels unfinished
* what is missing
* what visitors will remember
* what feels like a template
* where the experience loses energy
* where interactions could become more memorable
* where technical problems actually affect the experience

Do not immediately start editing the first file you see.

---

# 7. USE TWO AUDIT CATEGORIES

Do not search only for problems.

Search for:

## A. PROBLEMS

Something currently exists but is weak.

Examples:

* weak hero
* generic project cards
* poor hierarchy
* broken mobile layout
* mediocre typography
* awkward interaction
* inconsistent motion
* repetitive sections
* weak project presentation

## B. OPPORTUNITIES

Something valuable is currently MISSING.

* interactive project index
* cinematic case-study opening
* unique navigation
* memorable footer
* interactive About
* better project discovery
* stronger motion language
* project-specific visual worlds
* better transitions between sections

A technically perfect website can still fail creatively because important opportunities are missing.

---

# 8. FIND EVERYTHING, IMPLEMENT SELECTIVELY

Audit broadly.

Implement selectively.

Classify findings:

## P0 — BLOCKER

Broken functionality, major UX failure, serious regression.

Fix immediately.

## P1 — TRANSFORMATIVE / HIGH IMPACT

Changes that clearly improve how visitors perceive the portfolio.

Highest priority.

## P2 — SIGNIFICANT

Clearly useful and noticeable improvements.

Do after P1 or bundle with related work.

## P3 — POLISH

Small finishing improvements.

Defer until major work is strong.

## P4 — MICRO

Barely perceptible differences.

Usually ignore.

---

# 9. NEVER CREATE A DEVELOPMENT ROUND FOR MICRO WORK

Examples of work that should almost never receive a dedicated iteration:

* 1px spacing changes
* 2px spacing changes
* insignificant padding adjustments
* opacity 0.72 → 0.75
* border radius 11px → 12px
* animation 420ms → 450ms
* tiny shadow modifications
* microscopic alignment
* trivial code cleanup
* utility renaming
* tiny bundle reductions
* minor refactors with zero visible impact
* repeatedly validating already-passing systems

Do not waste meaningful tokens on invisible improvements.

---

# 10. MICRO-FIXES ARE ALLOWED WHEN THEY ARE FREE

If you are already modifying an important component and notice a small issue nearby:

fix it.

Example:

You are substantially upgrading project cards.

While doing so you notice:

* one spacing inconsistency
* one focus issue
* one small breakpoint bug

Fix them at the same time.

This is efficient.

What is forbidden is dedicating another entire iteration to those tiny issues.

---

# 11. USE AN IMPACT / COST MENTAL MODEL

Before choosing major work, roughly evaluate:

**VALUE =**

visitor visibility
× visual impact
× creativity improvement
× storytelling improvement
× number of areas improved
× memorability

divided by:

implementation complexity
× regression risk
× token cost

Do NOT waste tokens literally calculating this.

Use it as a decision principle.

---

# 12. ALWAYS SEEK LEVERAGE

Prefer improvements that affect multiple parts of the portfolio.

Excellent examples:

* stronger global typography
* stronger shared project component
* better shared transition system
* better motion primitives
* improved media treatment
* better case-study primitives
* better responsive grid
* stronger global spacing logic
* better visual hierarchy
* better route transitions

One strong systemic improvement can be worth dozens of individual fixes.

---

# 13. FIX ROOT CAUSES

Example:

title
paragraph
three cards

The root problem may be:

**repetitive composition.**

Improve the composition system.

Root-cause improvements have far higher leverage.

# 44. DO NOT REFACTOR WITHOUT A REASON

Refactor when it:

* fixes a real bug
* reduces meaningful complexity
* improves maintainability of frequently changed code
* prevents regressions

# 45. DO NOT RE-AUDIT UNCHANGED SYSTEMS

If something has already passed and related code has not changed:

Examples:

* cursor instance counts
* SPA DOM cleanup
* route cleanup
* accessibility states
* already-stable interactions
* previously verified performance behavior

---

# 46. VALIDATION MUST BE PROPORTIONAL

Use appropriate testing for the work performed.

### Small visual change

Inspect affected area.

### Shared component change

Inspect affected routes.

### Navigation change

Test routing and transitions.

### Motion change

Check performance and reduced motion.

### Major shared infrastructure change

Run broader validation.

### Final launch

Run comprehensive validation.

Do not run the maximum verification suite after every minor change.

# 72. SCREENSHOT TEST

Ask:

Would a still screenshot of the major sections look strong enough to appear in a world-class design gallery?

If not:

composition may need improvement.

But remember:

the interactive experience should be even better than the screenshot.

# 73. INTERACTION TEST

Ask:

Would removing all animation make the site lose a meaningful part of its identity?

If no:

motion may currently be generic decoration rather than true interaction design.

---

# 74. TEMPLATE TEST

Ask:

Could this same design belong to 500 different designers?

If yes:

strengthen personality and specificity.

---

# 75. CONTENT TEST

Ask:

Does this site communicate:

* who created it
* what they are good at
* what makes their work different
* what kind of work they want
* how they think
* why somebody should contact them

If not:

improve storytelling.

# 79. DEFINITION OF A SUCCESSFUL MAJOR ITERATION

At least one of these should clearly improve:

# 80. DEFAULT EXECUTION LOOP

Use this workflow:

## STEP 1 — INSPECT

Understand the current rendered portfolio.

## STEP 2 — AUDIT

Find problems AND opportunities.

## STEP 3 — PRIORITIZE

Rank by impact-to-cost.

## STEP 4 — USE TOOLS

Use relevant Skills, MCP, plugins, browser, research, documentation, code tools, etc. when useful.

## STEP 5 — CONCEPT

Choose the strongest high-impact solution that fits the current portfolio.

## STEP 6 — IMPLEMENT

Build it without unnecessarily rebuilding the rest of the project.

## STEP 7 — VISUALLY INSPECT

Judge the actual rendered result.

## STEP 8 — REFINE

Fix meaningful problems.

## STEP 9 — VALIDATE

Run proportional checks.

## STEP 10 — RECORD

Briefly update project progress if appropriate.

## STEP 11 — REASSESS

Find the next highest-impact weakness or opportunity.

Repeat.

# 82. VERY IMPORTANT EXAMPLE

# 83. NEVER CONFUSE MAINTENANCE WITH CREATIVE PROGRESS

Maintenance keeps the site healthy.

Creative development makes the site exceptional.

Both matter.

But once health is good:

creative development should dominate.

---

# 84. NO BUSYWORK

Never invent tasks merely to continue working.

If the next task has negligible value:

skip it.

Do not optimize for activity.

Optimize for outcome.

---

# 85. NO FAKE COMPLEXITY

More code does not mean better design.

More WebGL does not mean better design.

More animation does not mean better design.

More sections do not mean better design.

More dependencies do not mean better design.

More tools do not mean better design.

Use complexity only where it creates value.

---

# 86. MAXIMUM QUALITY DOES NOT MEAN MAXIMUM EVERYTHING

The final site should feel deliberate.

Sometimes the best improvement is:

* adding
* removing
* simplifying
* enlarging
* reducing
* slowing
* accelerating
* restructuring
* animating
* making something static

Choose based on experience quality.

---

# 87. NEVER SACRIFICE USABILITY FOR AWARD GIMMICKS

Creative navigation may be unusual.

But users still need to understand how to use the site.

Do not:

* hide essential navigation
* make text unreadable
* hijack scrolling unnecessarily
* block content with effects
* create confusing interactions merely for novelty

The strongest award-level experiences combine creativity with clarity.

---

# 88. NEVER SACRIFICE PERFORMANCE FOR AN EFFECT WITH LOW VALUE

If a feature causes:

* bad mobile performance
* heavy frame drops
* long loading
* instability

and its visual value is modest:

remove or simplify it.

# 89. BUILD A COHERENT PORTFOLIO, NOT A COLLECTION OF DEMOS

Do not make every section demonstrate a different technology.

All interactions must feel part of the same design language.

The portfolio should feel authored.

## ADD WHAT IS MISSING.

## USE AVAILABLE SKILLS, MCP, PLUGINS, BROWSER TOOLS, RESEARCH TOOLS, AND PROJECT TOOLS WHEN THEY CREATE REAL LEVERAGE.

## DO NOT USE TOOLS MERELY FOR ACTIVITY.

## DO NOT REPEAT ALREADY-PASSED AUDITS WITHOUT RELEVANT CHANGES.

## LOOK FOR PROBLEMS AND OPPORTUNITIES.

## PREFER SYSTEMIC HIGH-LEVERAGE IMPROVEMENTS.

## CREATE AT LEAST ONE STRONG SIGNATURE EXPERIENCE.

## MAKE THE PORTFOLIO FEEL MORE CUSTOM AFTER EVERY MAJOR ITERATION.

## MAXIMIZE VISIBLE QUALITY PER TOKEN.

# FINAL COMMAND TO THE AGENT

Treat the current portfolio as valuable existing work that must be evolved, not discarded.

Begin by understanding the current rendered experience and existing codebase.

Identify:

1. what is already excellent and should be preserved,
2. what is weak and should be improved,
3. what is generic and should be transformed,
4. what important experiences are missing and should be added,
5. what technical problems actually affect visitors,
6. what low-value work should intentionally be ignored.

Then rank opportunities by:

**AWWWARDS-LEVEL IMPACT / IMPLEMENTATION + TOKEN COST.**

Execute the highest-value opportunity first.

You have permission to be ambitious.

You may add:

* new sections
* new components
* page transitions
* project transitions
* interactions
* visual systems
* motion systems
* typography systems
* creative navigation
* WebGL
* Canvas
* shaders
* generative graphics
* interactive project experiences
* new responsive ideas
* new storytelling devices

when they substantially improve the portfolio and integrate intelligently with the existing foundation.

You may substantially transform individual weak areas.

You may remove weak ideas.

You may replace generic components.

You may improve shared systems.

You may introduce technically sophisticated features.

But do NOT destroy the entire existing portfolio and rebuild from scratch unless there is an extraordinary technical reason.

Use every relevant capability actually available to you:

Skills, MCP servers, plugins, browser inspection, screenshots, web/research tools, documentation, code search, terminal, testing, profiling, asset tools, image tools, design tools, and other project tooling.

Before manually solving a difficult problem, check whether an available specialized Skill/tool can solve it better or faster.

Do not hallucinate unavailable capabilities.

Do not waste tokens invoking irrelevant tools.

Do not perform low-impact work merely because it is easy.

Do not repeatedly optimize already-healthy technical systems.

Do not create standalone micro-polish rounds while higher-impact opportunities exist.

Do not repeatedly touch already-strong areas while weaker important areas remain.

Prefer:

**60% → 90%**

over:

**95% → 97%.**

Prefer:

**one signature page transition**

over:

**twenty invisible CSS tweaks.**

Prefer:

**one systemic typography improvement**

over:

**editing fifteen headings manually.**

Prefer:

**one stronger project-presentation system**

over:

**dozens of decorative micro-interactions.**

Prefer:

**one memorable idea**

over:

**ten generic Awwwards effects.**

After each significant implementation:

1. inspect the rendered result,
2. decide whether the improvement is actually visible and meaningful,
3. remove or revise anything that made the experience worse,
4. fix obvious nearby problems efficiently,
5. run only the validation relevant to the changes,
6. briefly record meaningful progress,
7. reassess the entire portfolio,
8. choose the next highest-impact weakness or opportunity.

If you catch yourself spending multiple actions on tiny spacing, tiny timing, tiny optimizations, invisible refactors, repeated audits, or long progress reports:

STOP.

Zoom out.

Find a more important problem or opportunity.

The goal is NOT to maximize the amount of work performed.

The goal is NOT to maximize technical complexity.

The goal is NOT to maximize animation.

The goal is NOT to maximize tool usage.

The goal is:

# MAXIMUM AWWWARDS-LEVEL QUALITY PER TOKEN.

Every substantial iteration should make the portfolio more:

* beautiful
* original
* intentional
* memorable
* immersive
* coherent
* premium
* expressive
* usable
* technically confident

A normal visitor should be able to SEE or FEEL the improvement immediately.

If the difference exists mainly in a changelog, it was probably not worth a major iteration.

Continue until the remaining weaknesses are genuinely small enough that major creative changes would create more risk than value.

Only then enter final micro-polish and launch-audit mode.
